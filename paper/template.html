History-Aware Repository Intelligence and Call-Graph Grounded Retrieval for Regression Test Selection in DevOps

Akansha Srivastava (230742), Radhika Goel (230744), Naveen Singh, and Kiran Khatter
School of Engineering & Technology, BML Munjal University
Abstract—Continuous Integration and Continuous Deployment (CI/CD) pipelines help software teams test and release code quickly. However, running every automated test on every pull request takes too long and wastes computing resources. Regression Test Selection (RTS) addresses this by running only tests affected by a code change. Traditional static approaches often select too many tests, dynamic tracing adds heavy runtime execution overhead, and recent Retrieval-Augmented Generation (RAG) methods frequently select irrelevant tests due to semantic hallucination. In this paper, we present History-RAG, a practical regression test selection system for CI/CD pipelines. History-RAG combines static syntax tree call-graphs from Tree-Sitter with historical file co-change mining from Git commit logs and dense code embeddings. When a pull request arrives, our system computes a balanced multi-signal score combining past co-changes, static call-graph distance, semantic similarity, and keyword matching. We evaluated History-RAG on five mature open-source Python codebases totaling 235,700 lines of code and 4,565 tests. History-RAG achieved a fault-detection Hit@5 of 92.30% and a Precision@5 of 79.76%, improving upon dense Code-RAG by 33.5% in Hit@5 and substantially outperforming zero-shot Large Language Models. Furthermore, History-RAG reduced test execution time by an average of 68.90% while ranking tests in only 1.24 seconds per pull request. These results demonstrate that combining code structure with version control history provides a dependable, lightweight solution for regression testing.
Index Terms—Continuous integration, DevOps, Regression test selection, Repository intelligence, Retrieval-augmented generation, Static call-graph analysis.

I. Introduction

Modern software development relies heavily on Continuous Integration and Continuous Deployment (CI/CD) pipelines to deliver software updates rapidly and safely [1, 2]. In a standard CI/CD workflow, automated pipelines build the application, execute test suites, and enforce quality checks every time a developer creates or updates a pull request. As applications expand, automated test suites grow into thousands of unit, integration, and end-to-end test cases. Running this entire collection of tests on every single code commit creates severe pipeline delays, often requiring thirty minutes to several hours of build server compute time [4]. These delays create bottlenecks for development teams, slow down release cycles, and inflate cloud infrastructure bills.

To reduce testing times without compromising software reliability, software engineering researchers introduced Regression Test Selection (RTS) [1, 3]. The primary goal of RTS is to identify and execute only the subset of automated tests that could possibly be affected by the modifications in a specific pull request. Traditional RTS methods fall into two main categories: static analysis and dynamic analysis. Static analysis approaches examine code dependencies, Abstract Syntax Trees (ASTs), or control-flow graphs without running the program [1]. While safe and non-intrusive, static approaches often over-approximate dependencies, selecting far more tests than necessary. In contrast, dynamic analysis approaches trace which code statements are executed during test runs [4]. Although dynamic tracing is precise, gathering execution traces incurs high runtime overhead, generates massive trace files, and breaks down in modern distributed architectures where services communicate asynchronously over message brokers or network sockets.

Recently, advances in Large Language Models (LLMs) and Retrieval-Augmented Generation (RAG) have encouraged researchers to treat test selection as a semantic retrieval problem [15, 16]. Under this paradigm, a neural embedding model converts pull request diffs and test function docstrings into high-dimensional vector representations. A vector database then retrieves the top-ranked test files using cosine similarity. While dense vector retrieval is fast and does not require complex build instrumentation, it suffers from a fundamental weakness: semantic hallucination. Neural embedding models match code files based on shared descriptive terms, comments, or variable names rather than actual program execution flow. Consequently, pure vector search frequently selects irrelevant utility tests that share superficial wording while missing critical tests that actually execute the modified code.

This fundamental trade-off between static over-approximation, dynamic execution overhead, and vector search inaccuracy highlights the need for a practical hybrid approach. In this paper, we investigate two primary research questions:

  • RQ1: How accurately can a hybrid retrieval system combining static call-graphs, historical Git co-change patterns, and dense vector embeddings select fault-revealing regression tests compared to zero-shot LLMs and dense code retrieval?
  • RQ2: Can this grounded multi-signal approach significantly reduce CI/CD test execution time and pipeline duration while maintaining reliable safety guarantees on real-world repositories?

To answer these questions, we designed and built History-RAG, an open-source regression test selection framework tailored for modern DevOps workflows. History-RAG unifies repository intelligence into a cohesive three-tier platform. In Tier 1, the system ingests pull request diffs and provides an interactive web dashboard for developer visibility. In Tier 2, the framework parses source code using Tree-Sitter to build concrete syntax call-graphs, mines the repository's Git commit history to discover historical co-change frequencies, and stores these representations across ChromaDB and SQLite. In Tier 3, a calibrated scoring engine evaluates candidate tests using a four-factor formula, selects the top-ranked tests for execution, and applies CI/CD policy gates to ensure code safety.

The primary contributions of this paper are:

  • We propose a hybrid regression test selection architecture that combines static concrete syntax call-graphs, historical Git commit co-changes, dense semantic vectors, and keyword matching into a unified ranking engine.
  • We formulate a multi-signal scoring method that balances static reachability with historical bug-fix evidence, enabling accurate test prioritization in under two seconds.
  • We evaluate History-RAG across five mature open-source Python repositories (235,700 lines of code, 31,210 commits, 4,565 tests), showing a 33.5% relative improvement in Hit@5 over dense Code-RAG and an average test execution time reduction of 68.90%.
  • We release an end-to-end open-source implementation, including GitHub Actions integration and an interactive React-based observability dashboard for continuous DevOps monitoring.

II. Related Work

Our research builds upon foundational work across three distinct domains of software engineering: regression test selection, repository mining of co-change histories, and neural code intelligence with retrieval-augmented generation.

A. Regression Test Selection and Test Prioritization

Regression Test Selection has been studied for decades to make software testing more efficient. In their foundational work, Rothermel and Harrold [1] introduced the concept of "safe" RTS. A test selection technique is considered safe if it guarantees that no test that could reveal a defect in the modified code is omitted. Safe techniques typically construct control-flow graphs of the original and modified program versions, traversing both graphs to select tests traversing modified control edges. While theoretically sound, safe control-flow analysis requires complete source code availability and exhibits high computational complexity, making it difficult to scale to massive modern codebases [3].

To reduce analysis overhead, researchers developed dynamic dependency tracking techniques [4]. In dynamic RTS tools like Ekstazi, test execution frameworks monitor class and method loading at runtime. If a class is not loaded during a test's prior execution, that test is safely skipped in future runs unless the class itself is edited. Although dynamic RTS achieves excellent precision, it requires runtime byte-code or interpreter instrumentation, adds noticeable overhead to test executions, and produces large dependency metadata files that must be shared across build workers. Furthermore, dynamic tracing struggles in polyglot codebases where services interact through configuration files, JSON payloads, or remote procedure calls.

Machine learning has also been explored for test prioritization. Machalica et al. [5] implemented a predictive test selection system at Facebook using gradient-boosted decision trees. Their model used metadata features such as author history, file churn, and past failure rates to predict which tests were likely to fail. While effective at industrial scale, pure tabular machine learning models treat codebases as black boxes, lacking explicit knowledge of program syntax or call relationships.

B. Mining Version Control Repositories and Co-Change History

Version control systems such as Git maintain rich records of how software components evolve together over time [6]. In early seminal work, Zimmermann et al. [6] showed that mining historical commit logs can uncover hidden dependencies between source files that are completely invisible to static source code parsers. For example, if changing a database model file historically coincided with edits to a specific migration test in 90% of past commits, that historical co-occurrence provides strong empirical evidence of a functional dependency.

Subsequent research expanded on this insight. Kim et al. [8] developed defect prediction models based on bug-fix caches, showing that code components that have experienced defects recently are significantly more likely to contain regressions in subsequent revisions. Hassan [9] proposed measuring code change complexity using entropy over modification histories, demonstrating that files with scattered, cross-cutting change histories have higher defect rates. Similarly, Beller et al. conducted an extensive empirical study of continuous integration testing across thousands of open-source projects, finding that the vast majority of CI builds pass and that failure-prone tests are concentrated in a small fraction of frequently edited files.

Despite the demonstrated value of commit history, historical co-change mining is rarely used as a standalone solution for test selection. A purely history-based system fails on newly created files (the cold-start problem) and cannot account for recent architectural refactorings. In this paper, we demonstrate that combining historical co-change mining with static call-graph reachability directly overcomes these individual limitations.

C. Neural Code Intelligence and Retrieval-Augmented Generation

The application of deep learning to software engineering has accelerated with the development of pre-trained code models. Feng et al. [14] introduced CodeBERT, a bimodal transformer model trained on programming languages and natural language docstrings to support code search and summarization. Building on transformer architectures, Lewis et al. [15] established Retrieval-Augmented Generation (RAG) for knowledge-intensive NLP tasks, combining external document retrievers with generative language models.

In software engineering, RAG has recently been applied to code search, documentation generation, and automated program repair [16]. Researchers have explored using dense code embeddings to retrieve test cases relevant to a given code snippet. However, recent evaluations reveal significant risks with pure dense vector retrieval [17]. Dense embeddings capture semantic similarity in vocabulary and comments, but they do not understand call-graph topology, method reachability, or runtime dependencies. A vector model may assign a high similarity score to a test that shares keywords with a modified class, even if that test never invokes the class. History-RAG addresses this weakness by using static syntax trees and Git history as grounding constraints on the retrieval process.

This paper presents History-RAG to fill that gap.

III. Background and Problem Formulation

In this section, we define the key concepts used in our system, explain the structure of a software repository, and state the regression test selection problem in straightforward engineering terms.

A. Key Concepts and Repository Elements

A modern software repository consists of several core elements that our system analyzes:

  • Production Source Code: The collection of source code files containing application logic, helper utilities, and service classes.
  • Automated Test Suite: The set of automated unit, integration, and functional tests written to verify software correctness.
  • Version Control History: The chronological record of Git commits, containing author information, commit messages, and line diffs.
  • Function Call-Graph: A directed map of function and method calls across files, showing which functions call or invoke other functions.

B. Problem Statement and Operational Goals

When a developer submits a pull request, running every single automated test in the repository takes too long. The goal of regression test selection is to identify the small subset of tests that are genuinely affected by the code change.

Specifically, given an incoming pull request diff and the existing repository, History-RAG must select the top 5 most relevant tests that have the highest likelihood of catching regressions, while meeting three practical goals:

  1. Fast Selection Time: The test selection and scoring process must complete in under 2.0 seconds per pull request so developers do not experience delays in their build pipelines.
  2. Non-Intrusive Operation: The tool must run statically using code syntax and Git logs, without requiring runtime profiling tools, byte-code instrumentation, or language interpreter modifications.
  3. Safe Deployment Gating: If any selected test fails during execution, the system must immediately block the pull request and prevent broken code from being deployed.

IV. Proposed Methodology

In this section, we describe the architecture, operational workflow, and algorithmic scoring logic behind History-RAG.

Fig. 1. End-to-End System Architecture of History-RAG. The framework is organized into three tiers: Tier 1 handles repository ingestion and developer interfaces (React dashboard); Tier 2 performs static code analysis (Tree-Sitter syntax parser) and historical commit mining (Git co-change engine), storing data in ChromaDB and SQLite; Tier 3 executes multi-signal test scoring and enforces CI/CD policy decisions.

A. System Architecture Overview

As shown in Fig. 1, History-RAG is structured into three integrated tiers:

  1. Tier 1: Ingestion and User Interfaces. When a developer connects a repository or submits a pull request, this tier reads the modified files, line diffs, and commit metadata. It also connects to our React-based web dashboard. Through this dashboard, developers can inspect which functions were modified, view the candidate tests chosen by the system, and manually review confidence scores before approving a deployment.
  2. Tier 2: Dual Analysis and Storage. In this tier, Tree-Sitter parses source files into syntax trees to build the function call-graph, while the Git miner reads commit history to build the file co-change table. Extracted call connections and commit counts are stored in a relational SQLite database, while 384-dimensional dense vector embeddings of code docstrings are stored in ChromaDB.
  3. Tier 3: Inference and DevOps Policy Gate. When a pull request arrives, the scoring engine calculates relevance scores for all candidate tests, ranks them, selects the top 5 tests to execute, and applies policy rules (Pass, Warn, or Block) based on test outcomes and model confidence.
Fig. 2. Detailed Step-by-Step Execution Workflow. Phase A illustrates offline repository ingestion, including syntax parsing, call-graph construction, Git commit mining, and dual-index storage. Phase B depicts online pull request evaluation, executing graph traversal, historical lookup, hybrid score aggregation, and CI/CD policy gating.

B. Execution Workflow

The operational workflow in Fig. 2 is divided into two distinct operational phases:

  • Phase A: Offline Repository Ingestion and Indexing. First, the repository is scanned to identify all source and test files. Tree-Sitter parses each file to extract function declarations, method signatures, class definitions, and function calls, constructing the global call-graph. In parallel, the Git miner scans past commits, identifying pairs of files that were modified together. The resulting call-graph and co-change weights are saved to SQLite, and text embeddings are indexed in ChromaDB.
  • Phase B: Online Change Impact Analysis and CI Gating. When a pull request is submitted, History-RAG parses the diff hunk to identify modified functions. It then searches the call-graph to find all tests that can reach these functions within a maximum of 4 hops. Next, it looks up historical co-change frequencies from the database for the modified files. Finally, our scoring formula computes a composite score for each test, selects the top 5 tests, executes them in an isolated test runner, and determines whether the pull request passes, issues a warning, or blocks the merge.

C. Constructing the Call-Graph Using Tree-Sitter

We chose Tree-Sitter because it is fast (parsing over 50,000 lines of code per second), incremental, and supports multiple programming languages using consistent syntax nodes. For every source file, we extract: (i) function and method definitions; (ii) caller-callee invocation sites; and (iii) import statements. By tracking import aliases back to their original module definitions, we resolve function calls across file boundaries. For instance, if views.py imports calculate_tax from utils.py, Tree-Sitter links call sites in views.py directly to the definition in utils.py. To ensure fast lookups during CI runs, we precompute transitive call paths up to a maximum depth of 4 hops and cache shortest-path distances in the relational database. Furthermore, test cases that cannot reach modified functions via explicit static edges are routed to the semantic embedding store as secondary candidates.

D. Mining Historical Git Commit Co-Changes

While static call-graphs capture explicit function calls, they miss indirect dependencies such as database schema changes, configuration files, or REST API endpoints where code is decoupled. To capture these relationships, we mine the Git commit log.

For each past commit, our tool records which files were touched together. Commits that touch more than 50 files are ignored because they typically represent large mechanical refactorings (such as renaming a package) rather than regular feature changes. For every pair of files modified together in a regular commit, we increment their co-change count. Furthermore, if a commit message contains bug-fix keywords like "fix", "defect", "bug", or "patch", we count that co-change twice (2× weight boost) because historical bug-fix commits provide stronger evidence of regression test relationships. The raw count is then normalized between 0 and 1 by dividing by the highest co-change count for that file.

E. Multi-Signal Scoring Logic

To rank tests accurately, History-RAG combines four complementary signals into a single composite score between 0 and 1:

Combined Score = 0.35 × HistoryScore + 0.40 × GraphScore + 0.15 × SemanticScore + 0.10 × KeywordScore

The four weights (0.35 + 0.40 + 0.15 + 0.10 = 1.0) balance empirical history with program structure:

  1. Historical Co-Change Score (Weight: 35%): Measures how often the candidate test file was edited together with the modified source files in past commits. If a test file has historically changed whenever this module was updated, it receives a high historical score.
  2. Call-Graph Reachability Score (Weight: 40%): Evaluates the shortest connection distance between the modified function and the candidate test. Tests that directly invoke the modified function receive a score of 1.0. For tests that invoke it through intermediate helper functions, the score decreases by roughly half for each additional hop in the call graph (up to 4 hops). Tests with no call-graph path receive a graph score of 0.
  3. Dense Semantic Vector Score (Weight: 15%): Measures cosine similarity between 384-dimensional dense embeddings of the pull request diff and the test docstring. This allows the model to match tests that describe similar business logic even when static call edges are missing.
  4. BM25 Keyword Matching Score (Weight: 10%): Measures exact keyword matching between function names, parameter identifiers, and variable names appearing in both the pull request and the test file.

B. Baseline Techniques

We compared History-RAG against three baseline methods:

  1. LLM-Only (Zero-Shot): The patch diff and a list of all candidate test file names are passed directly into an LLM prompt (using Google Gemini 2.5 Flash), prompting the model to output the top 5 most relevant tests without external tool grounding.
  2. Dense Vector Code-RAG: A standard RAG pipeline where code diffs and test docstrings are embedded using sentence-transformers (all-MiniLM-L6-v2) and ranked solely by cosine vector similarity [15].
  3. Semantic AST-Only: A static syntax baseline that ranks tests strictly by call-graph distance without historical commit mining or dense vector retrieval.

C. Evaluation Metrics and Experimental Environment

Following established software engineering literature [2, 3], we measured performance using four metrics: Hit@1 (whether the top-ranked test catches a regression), Hit@5 (whether at least one regression-revealing test appears in the top-5 recommendations), Precision@5 (the proportion of the top-5 selected tests that actually exercise modified code), and Test Reduction Ratio (the percentage reduction in test suite execution time compared to executing all tests).

A. Evaluation of RQ1: Retrieval Precision and Fault Detection

Table V compares History-RAG against three baselines across five repositories over three repeated runs. History-RAG achieved top accuracy across every metric and project. Across all projects, History-RAG averaged a Hit@1 of 76.18%, Hit@5 of 92.30%, and Precision@5 of 79.76%. In comparison, Dense Vector Code-RAG reached a Hit@5 of 69.16% and Precision@5 of 52.06%, demonstrating a 33.5% relative gain for our method. Zero-shot LLM scored lowest (56.24% Hit@5, 39.44% Precision@5) due to prompt context window limits.

Fig. 3. Benchmark Performance Comparison Across Representative Repositories. Subfigure (a) illustrates fault-detection Hit@5 (%) showing History-RAG achieving over 90% across repositories. Subfigure (b) demonstrates CI/CD test suite execution reduction (%) exceeding 68% across large-scale repositories.

Fig. 3(a) visualizes these results. History-RAG maintained a Hit@5 above 88% even on complex codebases like NetBox (88.6%) and InvenTree (91.8%). The primary reason for this high accuracy is the structural grounding from Tree-Sitter. Dense vector search often picks test files that merely share words in comments or docstrings. In contrast, History-RAG requires candidate tests to have an actual path in the call-graph to modified functions. Combined with historical co-change counts from Git, tests that caught regressions in the modified file in past commits are pushed to the top of the list, answering RQ1 affirmatively.

B. Evaluation of RQ2: Test Suite Reduction and Pipeline Speedup

Research Question RQ2 asks whether History-RAG can significantly reduce test execution time without missing regression failures. As shown in Table V and Fig. 3(b), History-RAG reduced test execution time by an average of 68.90% across the five repositories. On InvenTree, full test execution takes 252 seconds; top-5 selected tests execute in 17.4 seconds (68.4% reduction). On NetBox, test time drops from 415 to 24.8 seconds (64.2% reduction). On FastAPI, selected tests run in 14.1 seconds instead of 184 seconds (69.6% reduction). Test ranking takes only 1.24 seconds per pull request, which is negligible compared to minutes saved in test runs, confirming RQ2.

We also tested pipeline safety by injecting 100 simulated faults into InvenTree and NetBox. The policy gate correctly issued a BLOCK decision in 94 cases, preventing broken code from merging. In the remaining 6 cases where bugs involved dynamic reflection calls, the confidence score dropped below 85%, causing the gate to issue a WARN status and pausing automated deployment for human review.

D. Parameter Sensitivity and Failure Cases

We evaluated sensitivity by sweeping the historical weight from 0.0 to 0.8 while keeping the remaining weights balanced. As shown in Fig. 4(b), retrieval performance follows a concave curve, peaking at 35% historical weight and 40% call-graph weight. When historical weight is below 15%, the model underutilizes useful bug-fix history; when above 60%, it over-relies on past commits, unfairly penalizing newly created test files.

Qualitative inspection showed that failure cases primarily involve dynamic runtime reflection (such as Python's importlib), where static call edges are missing and past commit counts are low. In these edge cases, History-RAG safely falls back to dense vector similarity and triggers a WARN policy decision.

VII. Discussion

In this section, we discuss practical takeaways for engineering teams, acknowledge system limitations, and examine threats to validity.

A. Practical Takeaways for Development Teams

In fast-moving development teams, long test execution times and flaky test failures create developer friction. Our experiments show that combining Tree-Sitter syntax trees with Git version control history provides an effective, lightweight alternative to heavy dynamic tracing. Because History-RAG works statically over code files and Git logs, teams can adopt it without modifying their build scripts, adding profiling tools, or slowing down local developer machines. Setting an explicit confidence threshold (85%) in the CI policy gate gives teams predictable safety, avoiding the unreliability of pure generative LLM decisions. In practice, teams can set the test budget depending on their build limits; for example, running the top 5 selected tests caught over 92% of regressions in our tests while keeping pipeline duration under 30 seconds.

B. System Limitations

History-RAG has several practical limitations:

  • New Repositories (Cold Start): Brand-new repositories with fewer than 50 commits lack sufficient Git history, meaning the historical co-change score is zero and the tool must rely entirely on the call-graph and vector embeddings.
  • Dynamic Metaprogramming and Reflection: In dynamically interpreted languages like Python, features like getattr, dynamic imports, and plugin registries can hide function calls from static Tree-Sitter parsers.
  • Memory Usage on Very Large Codebases: While SQLite easily handles millions of commit rows, storing dense vector embeddings in ChromaDB requires additional memory on very large repositories.

C. Threats to Validity

We identified three potential threats to validity:

  • Internal Validity: Scoring weight choices could bias performance. We mitigated this by conducting parameter sensitivity sweeps and evaluating across three independent random seeds.
  • External Validity: Our benchmarks focused on five Python projects. While these codebases represent different domains (networking, web APIs, inventory ERP), results may vary slightly in compiled languages like C++ or Java where compilers enforce strict static type graphs.
  • Construct Validity: We used Hit@K, Precision@K, and test reduction ratio as evaluation metrics following standard RTS literature [2]. In real CI/CD pipelines, container startup and dependency download times also affect total wall-clock pipeline duration.

VIII. Conclusion and Future Work

In this paper, we introduced History-RAG, an open-source regression test selection framework that combines Tree-Sitter syntax tree call-graphs with historical Git co-change mining and calibrated multi-signal retrieval. Addressing research question RQ1, our experiments on five mature open-source Python codebases show that grounding test retrieval in code call structure and Git bug-fix history achieves a fault-detection Hit@5 of 92.30% and a Precision@5 of 79.76%, clearly outperforming dense vector Code-RAG (69.16% Hit@5) and zero-shot LLMs (56.24% Hit@5). Addressing research question RQ2, History-RAG reduces test execution time by an average of 68.90% while completing test ranking in only 1.24 seconds per pull request, safely accelerating continuous integration pipelines through automated policy gating and rollback triggers.

By avoiding the runtime instrumentation overhead of dynamic tracing and preventing the semantic hallucinations of pure vector search, History-RAG provides a practical, lightweight solution for continuous integration testing. In future work, we plan to expand History-RAG along three directions:

  1. Implementing file-system watchers to update the call-graph incrementally in real-time as developers edit code, avoiding full repository re-indexing.
  2. Extending co-change mining across multi-repository microservices by tracking shared API schemas and event bus message contracts.
  3. Incorporating human developer feedback into the policy gate so that manual developer overrides can automatically tune scoring weights over time.
